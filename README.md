# CareClick Clinics — Appointment No-Show Prediction

An end-to-end capstone project for **CareClick Clinics**, a chain of eight clinics in four cities.
Missed appointments leave doctor slots empty, and management only finds out *after* clinic hours.
This project **cleans the booking data, flags risky bookings in advance, and turns free-text call-center notes into structured reasons for no-shows**.

> **All data is synthetic.** It was generated by [`src/generate_synthetic_data.py`](src/generate_synthetic_data.py) (seed 42). No real patients are involved.

---

## The four parts

| Part | Notebook / scripts | What it does |
|---|---|---|
| **1 · Python & data** | [`notebooks/01_data_cleaning_and_enrichment.ipynb`](notebooks/01_data_cleaning_and_enrichment.ipynb) | Cleans `Appointments.csv` (duplicates, 3 date formats, messy clinic / gender / specialty / yes-no values, bad ages, impossible dates), adds lead-time features, enriches each clinic with daily temperature from the **Open-Meteo API**, and exports a clean **16-column** table. |
| **2 · SQL (MySQL)** | [`sql/`](sql/), [`notebooks/02_sql_analysis.ipynb`](notebooks/02_sql_analysis.ipynb), [`src/load_to_mysql.py`](src/load_to_mysql.py) | Schema, data load, and 10 business queries: no-show rate by clinic, effect of lead time, monthly trend, clinic ranking inside each city (window functions), SMS effect, and more. |
| **3 · Machine learning** | [`notebooks/03_ml_models.ipynb`](notebooks/03_ml_models.ipynb) | Logistic Regression vs Decision Tree vs Random Forest, compared mainly on **recall**; the winner is tuned with `GridSearchCV`; the test set is used once. Every booking gets a risk score and band. |
| **4 · Generative AI** | [`notebooks/04_genai_followup_notes.ipynb`](notebooks/04_genai_followup_notes.ipynb) | **Gemini API + Pydantic schema** structures the first 10 follow-up notes; the findings are combined with the ML risk scores into a prioritised front-desk call list. |

## Results snapshot (latest verified run)

| | |
|---|---|
| Clean table | 11,964 bookings × 16 columns, no missing values, overall no-show rate **19.8 %** |
| Biggest drivers (SQL) | lead time (same-day bookings ≈ 18 %, **31+ days ≈ 43 %**), past no-shows (0 → 14 %, **3+ → 52 %**), SMS reminder (16 % vs 24 %) |
| Model choice | Validation recall: Logistic Regression **0.61**, Decision Tree **0.58**, Random Forest **0.48** → **Logistic Regression** chosen, then tuned (`C`, class weight) |
| Final test result (used once) | **Recall 0.62** · precision 0.36 · F1 0.45 · ROC-AUC 0.73 — 293 of 474 real no-shows caught |
| Risk bands | High-risk bookings really miss **46 %** of the time vs **24 %** (Medium) and **12 %** (Low) |
| Call list | 10 notes → prioritised P1–P5 front-desk actions in [`outputs/front_desk_recommendations.csv`](outputs/front_desk_recommendations.csv) |

*A "dummy" model that never predicts a no-show scores 80 % accuracy but 0 % recall — which is why accuracy is not used to judge models here.*

## The clean table (16 columns)

| # | Column | Meaning |
|---|---|---|
| 1 | `appointment_id` | unique booking id |
| 2 | `patient_id` | patient id |
| 3 | `gender` | M / F / Unknown |
| 4 | `age` | years (invalid or missing → median of all rows) |
| 5 | `scheduled_date` | day the booking was made |
| 6 | `appointment_date` | day of the appointment |
| 7 | `lead_days` | `appointment_date − scheduled_date` |
| 8 | `lead_quartile` | 1 (shortest wait) … 4 (longest); cut-offs from **all rows** |
| 9 | `clinic` | canonical clinic name |
| 10 | `city` | city of the clinic |
| 11 | `specialty` | canonical specialty |
| 12 | `sms_received` | 1 = reminder SMS sent |
| 13 | `insurance_covered` | 1 = covered by insurance |
| 14 | `previous_no_shows` | earlier missed appointments of the patient |
| 15 | `avg_temp_c` | mean temperature at the clinic on the appointment day (Open-Meteo) |
| 16 | `no_show` | **target** — 1 = patient did not turn up |

## Project rules — how each one is met

| Rule | Where |
|---|---|
| Fixed random seed **42** everywhere | data generator, train/val/test split, models, `GridSearchCV` / `StratifiedKFold` |
| Quartiles and medians on **all rows before splitting** | Notebook 01: age median, `lead_days` quartiles, clinic temperature medians; notebook 03 asserts nothing is left to impute |
| **Never use the test set for model selection** | Notebook 03: models compared and tuned on train / validation only (CV on the training split); the test set is scored once, at the end |
| Compare mainly on **recall** (imbalanced classes) | Selection rule = highest validation recall; tuning ranks by recall subject to a precision floor of 0.30 so "flag everyone" cannot win |
| **No API keys committed**; only free tools | Keys are read from environment variables / a git-ignored `.env`; `.env.example` holds placeholders. Everything used is free (Open-Meteo, Gemini free tier, MySQL Community, scikit-learn…) |
| Single public GitHub repo with notebooks, SQL, CSV outputs, README, `data/` | This repository |

## Design decisions worth knowing

- **Why `city` is not an ML feature:** it is fully determined by `clinic`.
- **Why risk scores are out-of-fold:** each booking is scored by a model that never saw it (cross-validated predictions inside train + validation; the final model for test rows), so the risk bands are not inflated by memorisation.
- **Why Part 4's priority rules are plain `if` statements:** front-desk managers can read and challenge them. The LLM is used for what it is good at — reading messy text — and the decision logic stays transparent.
- **Pydantic + enums:** Gemini must answer from a fixed list of reasons, and every reply is validated, so malformed output fails loudly instead of quietly polluting the data.
- **Temperature is probably a weak feature.** In the synthetic data, no-shows were *not* generated from the weather, so a near-zero effect is expected and is a useful sanity check.

## Limitations and next steps

- Synthetic data is cleaner and more linear than reality, which is why a regularised Logistic Regression wins; on real data, re-compare all three models.
- The decision threshold is the default 0.5 on balanced class weights; a production system should pick the threshold from the real cost of an empty slot versus an unnecessary reminder call.
- Only the first 10 notes are processed, as specified; the same code handles all 40 (`notes.head(10)` → `notes`).
- Never send real patient notes to an external API without the appropriate consent and data-protection review.
